# F6: материалы и снабжение — аудит и границы

## Фактическая модель 0.6.2

`Arhilab.procurement` в `arhilab/assets/core.js` вычисляет потребность из строк работ с `autoMaterial`, класса комплекта, `kitOverrides`, количества и ручных материалов. Позиции комплекта ссылаются на SKU `catalog.json`; расход каждого SKU в старом каталоге часто не задан, поэтому требуется ручное подтверждение количества и упаковки. Округление упаковок и резерв относятся к плану, не доказывают получение товара.

`project.purchases[workId:baseSku | manualMaterialId]` хранит qty, pack, reserve, actual, actualEntered, status и updated. Статусы «Нужно купить», «Заказано», «Оплачено», «Доставлено», «На объекте», «Возврат» не являются достоверным журналом частичных поставок. Данные остаются в старой зашифрованной модели и резервной копии; их нельзя автоматически превращать в полученные количества или расходы. `LocalEstimates.ensure` сохраняет `purchases` в исходной смете. Цена строки сметы остаётся её историческим snapshot. Каталог не копируется целиком в заявку.

## Новые сущности и связь

| Источник | Локальная модель 0.7 | PostgreSQL и sync | Смысл |
| --- | --- | --- | --- |
| Вычисленный комплект/ручной материал | Подсказка в закупочном листе | Не создаёт запись | Плановая потребность без факта закупки |
| Подтверждённая заявка | `project.procurementRequests[]` | `procurement_requests`, `procurementRequest` | UUID, объект, необязательные смета/этап/строка, SKU или ручное наименование, единица, количество, срок, исполнитель, статус |
| Факт получения | `project.procurementReceipts[]` | `procurement_receipts`, `procurementReceipt` | Отдельный UUID, заявка, количество, дата, примечание; частичные поступления складываются точно |
| Чек/денежный расход | `project.expenses[]` | F3 `expenses`, `expense` | Только по отдельному подтверждённому действию с явной валютой; статус заявки и поступление денег не создают |

Количество — положительная decimal строка с четырьмя знаками после точки, PostgreSQL `numeric(18,4)`. Активные receipts складываются без JS floating point. При новом поступлении сверх заявки сервер отклоняет запись; после сокращения заявки существующие факты не удаляются и требуется исправление с видимым превышением. `requested`, `ordered`, `partially_received`, `received`, `cancelled` — статусы заявки; количества receipts, а не статус, источник факта. Soft delete и revision позволяют конфликтное разрешение через Stage 4. Перекрёстные ссылки проверяются внутри организации и объекта. `created_by` задаётся сервером. Расходы и cost не включаются в operational projection.

Права: существующая консервативная политика `sync/push` — admin; manager читает заявки, worker только назначенные ему заявки, без стоимости/закупочных цен. Поля F3 Expense доступны только admin. Данные хранятся в существующем encrypted `data.enc` вместе с `f1Sync` queue; локальное изменение и запись в очередь фиксируются одним атомарным сохранением. Синхронизация не обязательна для локальной работы.

## Открытые границы

Исторический `purchases.status` и `actual` сохраняются, но не мигрируют в receipts/expenses без подтверждения фактического происхождения. SKU в backend — подтверждённый текстовый идентификатор и снимок наименования/единицы, а не внешний path. Серверу нужен согласованный каталог SKU для строгой проверки актуальности SKU; до появления серверного каталога UI выбирает только существующие материалы, а сервер проверяет форму и принадлежность строки сметы. Отдельные ручные материалы не получают искусственный комплект.

## API и идемпотентность

Все изменения идут через существующий `POST /api/v1/sync/push` (`procurementRequest` / `procurementReceipt`), чтение через `GET /api/v1/sync/pull` и согласованный `GET /api/v1/sync/snapshot`. Операции имеют stable `operationId` и `idempotencyKey`; PostgreSQL фиксирует результат вместе с изменением и курсором. Повтор после потерянного ответа возвращает duplicate исходного результата. Client queue хранится вместе с бизнес-данными в `data.enc` (AES-GCM, Android Keystore). Никакого второго sync engine или plaintext журнала нет.

`procurementRequest` create: `projectId`, необязательные `estimateId`, `stageId`, `estimateItemId`, `catalogSku`, `title`, `unit`, `requestedQuantity`, `status`, `neededByDate`, `assigneeId`, `note`. `procurementReceipt` create: `projectId`, `requestId`, `quantity`, `businessDate`, `note`. Автор всегда берётся из серверной identity; клиент не передаёт `createdBy`. Перемещение существующей заявки или поставки между объектами/сметами запрещено. Список допустимых SKU в backend генерируется из поставляемого `catalog.json`; unit test сравнивает наборы. Если каталог меняется, backend manifest обновляется в том же коммите. Фактические цены каталога в manifest не попадают.

При одновременном добавлении двух поступлений organization row lock сериализует транзакции; второй запрос видит сумму первого. Редактирование одной записи использует revision и сохраняет Stage 4 conflict; удаление заявки с историей поступлений отклоняется. Уменьшение заявки ниже уже полученного не удаляет историю и отображается как превышение. Снятие назначения worker даёт redacted tombstone в pull. Manager читает operational данные, worker — только назначенные заявки; receipts worker сейчас не отправляются в snapshot/pull. Admin создаёт/правит/удаляет. Все денежные расходы и закупочные цены остаются за admin.

Проекция в Today показывает просроченную/сегодняшнюю заявку или неполное получение без сохранения искусственной задачи. Сигнал вычисляется по датам и активным receipts. Локальные legacy закупки и расходы не преобразуются автоматически.
